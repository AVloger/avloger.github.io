一个线程对一个套接字做 `read`，数据没来就睡，数据来了再拷到用户态。这是最清楚的阻塞 I/O。它没错，只是接不住“一万个大部分时间都在等”的连接。

把线程改成非阻塞，`read` 立刻返回“现在没有数据”，调用方自己去轮询。连接一多，轮询本身会把 CPU 烧光。

I/O 多路复用把问题收成一句：让内核替你看着一批描述符，哪几个可读可写了再叫醒你。你仍然可能用一个线程做后续的 `read` / `write`。复用的是等待，不是拷贝。

```text
阻塞：一等一
非阻塞轮询：自己问一万次
多路复用：内核通知“这几个好了”
真正异步：内核把数据也准备好再通知
```

Linux 用户态网络服务里，真正铺开的是第三种。AIO 和 `io_uring` 在走第四种，但理解线上系统，先把前三种钉住。

---

## 1. 五种模型里，多路复用站在哪

UNIX 网络编程里的五种模型，差别在两件事：等的时候进程在不在跑，以及数据从内核到用户态是谁来搬。

- 阻塞：等数据、搬数据，都卡住调用方。
- 非阻塞：等数据时反复系统调用，搬数据时仍然同步。
- 多路复用：等的是“集合里谁就绪”，就绪之后的读写仍是同步的。
- 信号驱动：用信号代替你去 poll。
- 异步 I/O：等和搬都可以在内核完成后再回调。

所以“Nginx / Redis 是异步的”这种说法要拆开看。它们通常是多路复用加事件循环：通知是多路的，读写仍在事件循环线程里同步完成。这已经足够支撑高并发连接，因为它把线程数量从“连接数”降到了“事件循环数”。

---

## 2. select、poll、epoll 差在等待集合

三者都能同时盯很多描述符。真正拉开差距的是：内核怎么记住你关心谁，以及每次等待要搬多少状态。

`select` 把感兴趣的 fd 位图在用户态和内核之间来回拷。fd 数量有上限（历史上常是 1024），每次返回还要扫描整个集合，看哪一位被置上。连接少时够用，连接多时拷贝和扫描都线性变差。

`poll` 换成链表/数组，摆脱了 1024 这个硬顶，但每次仍要把整个兴趣列表交给内核，返回后再线性扫。上限松了，复杂度还在。

`epoll` 把兴趣列表放进内核里的一棵红黑树（实现细节随版本会变），用 `epoll_ctl` 增删改，用 `epoll_wait` 只取“已经就绪”的那一批。就绪队列让热路径不再扫一万个冷连接。

可以记成：

```text
select / poll：每次把“我关心谁”再说一遍
epoll：先登记，再只问“谁变了”
```

这就是为什么 C10K 之后的网络服务几乎都站在 epoll（或 kqueue、IOCP）这一侧。

## 3. 水平触发和边缘触发

水平触发（LT）：只要缓冲区里还有数据，`epoll_wait` 就会反复告诉你“可读”。漏读一次，下次还会提醒。写起来像 select，不容易饿死事件。

边缘触发（ET）：只在状态变化时通知一次，比如从不可读变成可读。你必须把数据读到 `EAGAIN`，否则内核不会再敲门。事件循环可以少被吵醒，代价是处理逻辑必须读干净、写到不能再写。

LT 适合先把正确性做稳。ET 适合你已经能保证每次唤醒都把该处理的 I/O 抽干。很多框架默认 LT，不是因为 ET 落后，而是因为漏事件的成本高于少几次唤醒。

---

## 4. 多路复用解决不了的事

`epoll_wait` 返回“可读”，不代表业务已经完成。后面还有协议解析、磁盘、数据库、锁。如果这些工作堵在同一个事件循环里，多路复用会退化成“一个很忙的单线程”。

所以高并发服务通常还要再切一刀：

- 网络等待放在事件循环里。
- 可能阻塞的业务放到线程池，或者改成异步接口。
- 文件 I/O 不要假设和套接字一样能被 epoll 漂亮地通知。

select / poll / epoll 比较的是通知机制。服务能不能撑住，还要看阻塞点有没有从内核等待，悄悄挪到你自己的业务代码里。
