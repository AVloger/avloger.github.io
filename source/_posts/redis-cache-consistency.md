缓存的本职是挡住重复读。它不是第二份事务存储。一旦把它当数据库用，就会在“要不要同步”上花掉所有时间。

先把流量打穿的方式和双写打架的方式分开。前者是读路径过载，后者是写路径看见了两份状态。

```text
读：key 不在缓存时，谁去打数据库
写：数据库改了，缓存什么时候变成对的
```

---

## 1. 穿透、击穿、雪崩

穿透：查询根本不存在的数据。缓存没有，数据库也没有，每次都落到存储。恶意扫不存在的 ID，会把数据库打穿。挡法是：对空结果也缓存一小段时间，或者用布隆过滤器先否决明显不存在的 key。空缓存要设短 TTL，避免真数据写入后还被空值挡很久。

击穿：一个热点 key 过期，瞬间所有请求去打数据库。挡法是：热点不过期、只主动更新；或者过期时只放一个线程去回源，其余等。它和穿透的差别是：key 本来存在，只是在过期窗口变成了热点。

雪崩：大量 key 在同一时刻过期，或者缓存进程本身挂了。流量一起落到数据库。TTL 加随机抖动，避免整点一起死；缓存高可用和本地限流，避免“缓存没了就等于数据库裸奔”。雪崩是容量规划问题，不是再设一个 `expire` 能单独修好的。

这三种都是读路径的失败模式。它们不保证写路径两边相等。

## 2. 双写没有正确，只有更不容易错的顺序

先更新数据库，再删缓存。读请求如果夹在这两步中间，可能把旧值又写回缓存。延迟再删一次，是在赌：等并发读结束，把那次脏回填清掉。它降低脏窗口，不消灭脏窗口。

先删缓存，再更新数据库。删完到写完之间的读，会把旧数据库值填回缓存，脏得更明确。所以常见建议是“先库后缓存，失败就删”。删比改更安全：删错了只是少一次命中，改错了会把错值留到过期。

![双写窗口](/images/redis-cache-consistency/02-double-write.png)

![先删缓存](/images/redis-cache-consistency/03-delete-cache.png)

![先更新数据库](/images/redis-cache-consistency/04-update-db.png)

更新缓存而不是删除，等于在应用里维护第二份数据。字段映射、部分更新、并发写，都会把缓存变成难维护的副本。除非读远多于写、且你能接受最终一致，否则删比改干净。

跨机、跨进程没有事务能同时罩住 Redis 和 MySQL。消息队列、订阅 binlog 去删缓存，是在把“谁负责让缓存失效”从业务代码里挪到异步管道。延迟更长，重试更清楚，仍然是最终一致。

---

## 3. 限流往往比再加一层缓存更先该做

缓存击穿时，真正要命的是数据库连接和磁盘。回源加锁、空值缓存、布隆过滤器，都是在减少打到存储的并发。如果入口没有限流，这些手法只是把打穿的时间往后挪。

分布式限流用计数器、滑动窗口或令牌桶。放在 Redis 里只是因为计数本身需要一个快的共享状态。限流的对象是入口 QPS 和回源并发，不是“把缓存策略写得更花”。

一致性要求一旦强到“读必须看见刚提交的写”，最干净的做法常常是：这条读不要走缓存，或者写完后读主库。缓存适合能忍受片刻旧值的读。把强一致读硬塞进缓存，会把双写协议堆成无法复查的状态机。

---

## 4. 可以复查的判断

出现脏数据或数据库被打满时，先归类：

1. 不存在的 key 反复回源：穿透。
2. 单个热点过期：击穿。
3. 一片 key 一起失效或缓存挂了：雪崩。
4. 写库成功但读到旧缓存：双写窗口。

归到 1-3，先做空值、单飞、TTL 抖动和限流。归到 4，先承认最终一致，再选“先库后删”还是订阅变更去失效。不要用同一套“再加一层 Redis”去治四类不同的病。
