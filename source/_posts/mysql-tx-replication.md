事务承诺的是一组语句要么一起成功，要么一起看不见。InnoDB 把这个承诺拆成几件可以单独讨论的事：并发时看见什么（隔离），崩溃后能不能回到已提交状态（redo / undo），别的机器能不能跟上（binlog / 复制），单机写不下时怎么切开（分片）。

混在一起背 ACID，遇到主从延迟或分库分表，就会发现“事务”这个词已经不够用。

```text
隔离：当前实例里，读能看见哪一版行
持久：这个实例崩溃后，提交还在不在
复制：别的实例能不能重放同样的提交
分片：提交还过不过单机边界
```

---

## 1. 隔离级别在限制可见性

读未提交：别人改了但没提交，你也可能看见。脏读出现在这里。InnoDB 默认不用它。

读已提交（RC）：每次语句看到的是该语句开始时已经提交的版本。同一个事务里两次读同一行，中间别人提交了，你可能读到不同值。不可重复读是它的特征，不是 bug。

可重复读（RR）：InnoDB 默认。事务开始后，普通 SELECT 看到的快照尽量保持一致。当前读（`SELECT ... FOR UPDATE`、更新删除）仍要读最新版本并加锁。幻读在 RR 下被 Next-Key Lock 这类间隙锁压住一部分，但不要假设所有语句都在快照里。

串行化：读写都往锁上靠，把并发几乎收成排队。正确性最强，吞吐最差。

MVCC 让读大多不必阻塞写。行上挂着版本链，undo 里留着旧版本。读走快照，写走当前行加锁。于是“为什么更新会等，查询却还能过”就说得通：它们走的不是同一条读路径。

## 2. 三份日志各管一段失败

undo：事务要回滚，或者别人要读旧版本，都靠它。长时间不提交的事务会拖住 undo 清理，表空间和查询都会变丑。

redo：Buffer Pool 里的脏页还没刷盘，实例就死了。恢复时用 redo 把页补到足够新。它保证的是已提交事务的修改不会丢，不是“数据页随时都是最新的”。

binlog：Server 层的逻辑日志，给复制、备份、以及某些恢复路径用。它不替代 redo。崩溃恢复靠 redo；把变更送到从库靠 binlog。

提交要把两边对齐。只写了 redo 没写 binlog，主库自己恢复得了，从库会缺一次提交。只写了 binlog 没把 redo 持久化，主库恢复后可能和从库对不上。两阶段提交不是仪式，是这两份日志格式不同逼出来的协议。

## 3. 主从复制在卖读扩展，不是同步事务

从库本质是：把主库 binlog 拉过去重放。异步复制里，主库提交成功不代表从库已经执行完。半同步把“至少有一个从库收到日志”抬进等待条件，仍然不是跨机事务。

于是你会看到：

- 读从库可能读到旧值。
- 主库崩溃时，尚未送到从库的提交会丢（异步）或被限制（半同步 / Group Replication）。
- 复制中断后，先要问的是位点，不是“重启一下”。

主从解决的是读扩容和备份窗口。它不把单机事务自动升级成多机事务。

## 4. 分库分表切开的是数据，也切开了事务

单表太大、单机写不下时，按某个键把数据拆到多张表、多个库。查询如果带这个键，可以落到一台；跨键、跨库的事务和 JOIN 立刻变难。

分片键一旦选错，后面所有 SQL 都在还债。按用户 ID 切，适合用户维度的读写；按时间切，适合归档，不适合“查这个用户所有订单”这种跨片访问。分布式事务、全局主键、跨库一致性，都是在补“事务过不了单机边界”的缺口。能避免跨片更新，就不要先上 XA。

## 5. 可以复查的判断

讨论 MySQL 一致性时，先声明你站在哪一层：

1. 同一实例、两个并发事务：隔离级别和锁。
2. 同一实例、进程被杀：redo / undo。
3. 两个实例：binlog 和复制延迟。
4. 两台互不复制的分片：你已经离开单机事务。

层说清楚了，才知道该调隔离级别、该看日志刷盘，还是该承认分片后不再有原来的事务。
