程序是磁盘上的静态指令和数据。进程是操作系统把这份静态材料装进一套运行环境之后的结果。

这套环境至少包括：独立的虚拟地址空间、打开的文件描述符、凭证与权限、以及一份记录当前跑到哪一步的控制信息。内核用进程控制块（PCB）保存这些信息。没有 PCB，内核就没法在中断、系统调用和调度切换之后，把一个进程完整地接回来。

一句话概括：

> 进程是资源分配和保护的单位。CPU 时间片只是它在某一时刻借到的执行权。

```text
程序（静态）
-> 进程（地址空间 + 资源 + 状态）
-> 线程（同一地址空间里的执行流）
```

## 1. 进程状态在表达什么

教科书里的五态模型够用：新建、就绪、运行、阻塞、终止。Linux 里更常见的是 `R`（可运行）、`S`（可中断睡眠）、`D`（不可中断睡眠，多半在等磁盘）、`T`（停止）、`Z`（僵尸）。

这些字母不是装饰。它们在回答一个工程问题：这个执行流现在卡在哪一层。

![进程的状态转换](/images/os-process-model/02-process-state.png)

![Linux 进程状态](/images/os-process-model/03-process-state-linux.png)

- 就绪 / `R`：想跑，但 CPU 还没轮到它。
- 阻塞 / `S`：在等事件，比如读套接字、等锁、等子进程。事件来了才会回到就绪。
- `D`：在等底层 I/O，信号也打不醒。磁盘卡住时，一堆 `D` 状态往往比 CPU 打满更危险。
- 僵尸：子进程已经退出，父进程还没 `wait`。资源大部分已经释放，留下的是退出码。

CPU 密集任务长时间停在运行态，把时间片用完再回就绪队列。I/O 密集任务会频繁进入阻塞。所以“这个服务是 CPU 密集还是 I/O 密集”不是面试口头禅，它直接决定你该加核、加并发，还是先把 I/O 路径打通。

## 2. 调度器在选什么

调度器的输入是就绪队列，输出是“下一个占用 CPU 的执行流”。目标互相打架：吞吐、延迟、公平、实时。

常见策略各有适用面：

- FCFS / 时间片轮转：实现简单，短任务可能被长任务拖死，或者频繁切换把缓存冲掉。
- 优先级：紧急任务能插队，没有老化就会饿死低优先级任务。
- CFS：Linux 默认用虚拟运行时间逼近公平。它不是“谁优先级高谁一直跑”，而是让每个任务按权重拿到相近的 CPU 份额。

![作业调度、内存调度和进程调度](/images/os-process-model/05-three-level-scheduling.png)

工程上真正要盯的，往往不是算法名字，而是这几件事：

1. 可运行任务是不是远多于核数（排队）。
2. 有没有任务长时间跑在一个核上，把缓存吃热；或者被频繁迁移，把缓存吃冷。
3. 有没有 I/O 等待被误判成“CPU 不够”。

把 CPU 打满和把延迟打高，是两类病。调度只能治第一类里的一部分。

## 3. 进程和线程的隔离边界

进程之间默认看不到对方的全局变量。要交换数据，必须走内核提供的通道。这个隔离换来的是崩溃互不影响、权限可以分开授。

线程共享同一地址空间。创建更便宜，通信可以直接读写内存，代价是一个线程踩内存，整个进程一起死；锁、可见性、取消也全部变成共享问题。

![线程与进程](/images/os-process-model/04-thread.png)

所以选择不是“线程更先进”，而是：

```text
要隔离和独立生命周期 -> 进程
要共享内存和轻量切换 -> 线程
要用户态调度海量任务 -> 协程 / goroutine 这一类运行时
```

用户态调度把阻塞点从操作系统线程上挪走，本质仍是：谁在等 I/O，谁不该占着内核线程。Go 的 GMP 是这条线上的一个实现，不是操作系统另造了一种进程。

---

## 4. 可以复查的判断

看一个进程出了什么问题，先问三句：

1. 它现在是在跑、在等、还是已经退出？
2. 等的是 CPU、锁、网络，还是磁盘？
3. 它和别的执行流之间，隔离边界画在进程、线程，还是用户态任务？

状态、调度、隔离边界这三件事清楚了，后面的进程间通信、I/O 多路复用和虚拟内存才有地方挂。
