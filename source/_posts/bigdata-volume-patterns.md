所谓海量，就是数据没法按你习惯的方式一次性放进内存，或者放得进去也来不及在限定时间里扫完。解法很少是换一种更炫的内存结构，而是先承认约束，再把问题切小。

```text
装不下 -> 切块，块内能处理，块间再合并
要对齐同一类 key -> 哈希到同一台 / 同一文件
只要在不在 -> 位图或布隆过滤器
```

这和分布式计算框架要做的事是同一类：把大问题变成能放进一台机器的小问题，再定义小问题之间怎么交换。MapReduce 的 shuffle，本质上就是“相同的 key 必须见面”。

---

## 1. 分治：先变成能排序、能计数的文件

十亿条查询日志求 TopN、求重复 URL，单机内存可能只够几千万条。外排的做法是：切成能放进内存的块，块内排序写回，再多路归并。TopN 在归并时只保留堆里的 N 个。重复检测可以在每个有序块里做，再在归并时把相邻相同的键合并。

切块的依据是内存，不是“平均分成 100 份”这种口头数。块太大，内部排序会换页；块太多，归并的路数会把同时打开的文件打满。这是单机版的分区。

如果问题是“两个大集合的交集”，也可以各自切块、各自排序，再像归并一样对两路指针。不必先把两边都读进 HashSet。HashSet 只在“较小的一边能进内存”时才是好策略。

---

## 2. 哈希分片：让相同的键自己碰头

有些问题不需要全局有序，只需要相同的 key 在同一处出现。把 key 哈希到 0..M-1，写成 M 个文件或发到 M 台机器。每个分片内部再用内存哈希表或排序处理。倾斜时，热 key 会把某一个分片撑爆，这时要二次切分热 key，或把热 key 单独流水线处理。

这就是单机模拟 MapReduce：map 负责把记录打到分区，reduce 负责分区内聚合。集群上 Spark / Flink 做的是同一件事，只是把文件换成网络 shuffle，把失败重试做成框架。

查询“这个 ID 在不在十亿个数里”，如果允许误判，不必真的分片存全量。那是下一类问题。

---

## 3. bitmap：存在性可以按位买

整数域已知且不太大时，用一位表示在不在。十亿个不超过 32 位的整数，用 bitmap 大约 512MB 量级就能做存在判断和去重计数。交集并集是按位运算。广告标签、登录日活、权限位，都是在吃这套密度。

![bitmap](/images/bigdata-volume-patterns/01-bitmap.png)

整数域极大、只是要判断“见过没有”，布隆过滤器把多个哈希映射到位数组上。空间更省，代价是有假阳性：说在，可能不在；说不在，一定不在。缓存穿透时用它挡明显不存在的 key，就是在买这种不对称错误。

HyperLogLog、Count-Min Sketch 继续往近似走：要的是基数或频率的数量级，不是精确名单。海量处理里，精确和近似是两种产品。先问业务能不能接受错，再选结构。

---

## 4. 可以复查的判断

接到一个“海量”题目或线上数据任务，先写约束：

1. 单机内存上限是多少？数据是否必须精确？
2. 相同的 key 必须见面吗？见面的粒度是记录、用户，还是时间窗口？
3. 热 key 会不会摧毁某个分片？

能进内存就不要外排。必须精确去重就不要布隆。必须跨机器聚合，再谈框架和 shuffle。海量数据处理的核心不是背一套题，而是把“装不下”翻译成可执行的切法和错误预算。
