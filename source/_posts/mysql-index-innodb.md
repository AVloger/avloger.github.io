索引不是给语句贴的加速标签。它是另一种数据布局：让定位某一行、某一段行时，少碰磁盘页。

InnoDB 用 B+ 树。叶子节点串成链表，等值查找走树高，范围查找在叶子上顺序走。树高通常很小，所以“有没有合适的索引”差的是数量级，不是百分之几十。

```text
主键 / 聚簇索引：叶子就是整行
二级索引：叶子是主键值
回表：拿主键再回聚簇索引取行
```

## 1. 聚簇索引把行和主键绑在一起

InnoDB 表一定有聚簇索引。你定义了主键，主键就是聚簇索引；否则可能用唯一非空索引，再不行就给隐藏的 row id。叶子页上直接放行数据。按主键范围扫，物理上接近顺序读。

这意味着主键怎么选会写进整张表的布局。随机 UUID 当主键，插入会在叶子中间打洞，页分裂变多，缓冲池命中变差。自增或有序键把插入推到末尾，页更紧，缓存更好说话。这不是风格问题，是页怎么长的问题。

二级索引的叶子不放整行，只放主键。用二级索引找到记录后，还要拿主键去聚簇索引再找一次，就是回表。回表次数一多，二级索引的优势会被随机读吃掉。

## 2. 联合索引吃的是最左前缀

`(a, b, c)` 这棵树，排序键是 `a`，`a` 相同时按 `b`，再按 `c`。它能好好用上的条件，是从左边开始连续匹配的那段。

- `a = 1`：能用。
- `a = 1 AND b = 2`：能用。
- `b = 2`：不能指望这棵树帮你定位，因为 `b` 在树里不是第一排序键。
- `a = 1 AND c = 3`：通常只能用到 `a`，`c` 变成主键回表之后再过滤。

范围查询会截断后面的列。`a = 1 AND b > 10 AND c = 3` 里，`b` 一旦进入范围，`c` 很难再用来定位，最多当过滤。优化器具体怎么选，仍以执行计划为准，但这条截断规则能解释大部分“为什么我建了三列，只用上两列”。

覆盖索引是把查询需要的列都放进二级索引，避免回表。`SELECT b FROM t WHERE a = 1` 对 `(a, b)` 来说常常不必回主键。列加多了索引变胖，写放大也变大。覆盖不是免费的。

## 3. 慢查询先看扫描了多少

`EXPLAIN` 里值得先看的不是一堆缩写，而是：

1. 用了哪把 key。
2. `rows` 估计要碰多少行。
3. 是 `const` / `ref` / `range`，还是 `ALL`。
4. `Extra` 里有没有 `Using filesort`、`Using temporary`、`Using index`。

`Using index` 通常表示覆盖索引已经够用。`ALL` 加很大的 `rows`，就是在说：优化器觉得走索引还不如扫表。这时要问统计信息新不新、条件是否对索引不友好（函数包列、隐式类型转换、前导模糊 `%xx`），而不是先加第四个索引。

索引优化的顺序应当是：让条件能匹配最左前缀，让排序和分组尽量顺着索引走，让回表变少。硬件和分区是更后面的杠杆。把经常变的热数据放进缓存、把冷热列拆开，属于表设计和访问模式，不是给错误计划打补丁。

---

## 4. 可以复查的判断

给一张慢查询，先写三句话：

1. 这条语句的等值列、范围列、排序列分别是什么？
2. 现有索引的最左前缀能不能接住它们？
3. 接住之后还要不要回表？回表的行数能不能接受？

答得上来，索引讨论才是在谈 InnoDB 的数据布局。答不上来，加索引只是在表上再堆一棵不一定会被选中的 B+ 树。
