[上一篇](/posts/virtual-memory-basics/)把虚拟内存讲成地址空间、页表、TLB 和缺页。这篇只追一个后续问题：缺页发生时，如果物理页已经用完，内核踢哪一页？

这不是“磁盘当内存”的另一种说法。被踢的页可能写回 swap，也可能只是丢掉一份还能从文件再读回来的副本。两类页的代价差一个数量级。

```text
匿名页（堆、栈、私有映射） -> 没地方就得换出到 swap
文件页（page cache、文件映射） -> 干净页可以直接丢
```

---

## 1. 缺页之后会发生什么

MMU 走页表，发现这一页不在内存，或者权限不够，就会陷入内核。内核要区分：

- 还没建立映射：可能是第一次碰这个地址，按需分配物理页，必要时从文件读入。
- 页在 swap 里：从交换区读回来，改页表，刷新 TLB。
- 写了只读页：常见于 copy-on-write。fork 之后父子共享物理页，谁先写谁拷一份。
- 真的非法访问：给进程 SIGSEGV。

只有前两类会在内存紧张时触发置换。置换算法回答的是：从已经在内存里的页中，选一个牺牲品。

## 2. FIFO、LRU 和 Clock

FIFO 最早进来的最先出去。实现便宜，但会把刚用过、马上还要用的页换走，Belady 异常也出现在这类策略上：给更多物理页，缺页次数反而可能增加。

LRU 近似“最久没人碰的页最不值钱”。局部性好的工作集下，它很接近理想。精确 LRU 需要每次访存都维护顺序，硬件和内核都嫌贵，所以实际系统用近似。

Clock / 二次机会是常见近似：页被围成环，每页有一个引用位。指针扫到引用位为 1 的页，把它清零并放过；扫到 0 就选它。热点页因为不断被置位，不容易被立刻踢掉。Linux 的活跃/非活跃 LRU 链表是这条思路的工程版，还要再拆匿名页和文件页。

没有放之四海都最优的算法。数据库缓冲池、操作系统 page cache、语言运行时堆，面对的访问模式不同，不能互相抄结论。

## 3. page cache 不是 swap

读文件时，内核通常先把数据放进 page cache。再读同一块，就不必回磁盘。写文件也可以先落到 cache，再按策略回写。这些页的“备份”在文件系统里，干净页被回收几乎没有内容损失。

swap 面对的是没有文件备份的匿名页。进程堆涨起来、语言运行时堆撑满、大块私有 mmap，都会变成匿名页。它们被踢出去，等于把进程的工作集写到磁盘。下一次碰这些地址，延迟从纳秒变成毫秒。

所以看到机器 “free 很少” 先别慌。Linux 喜欢把空闲内存拿去当 cache。真正危险的是：

1. 匿名页把 cache 挤光，读文件开始反复打盘。
2. 开始频繁 swap，延迟抖动，CPU 看起来不忙，业务已经超时。
3. OOM killer 选中了某个进程，直接杀掉，连换出的机会都不给。

`free`、`cache`、`swap`、`si/so` 要一起看。只看“内存用了百分之多少”，会把健康的 page cache 当成故障。

## 4. 可以复查的判断

内存问题拆成三层问：

1. 地址对不对、权限对不对？这是虚拟内存和页表。
2. 这一页有没有文件备份？这是 cache 还是匿名页。
3. 工作集是不是已经大过物理内存？这才轮到置换算法和 swap。

把这三层混成“内存泄漏”或“磁盘当内存”，后面的排查会从一开始就走偏。虚拟内存负责看见；页面置换负责在看不见的物理页上做取舍。
